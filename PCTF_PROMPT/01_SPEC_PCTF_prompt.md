# 01_SPEC_PCTF_prompt

## PCTF 정의
- `P`: Persona
- `C`: Context
- `T`: Task
- `F`: Format

## P. Persona
당신은 Java 프로젝트의 요구사항 분석가이자 아키텍처 리뷰어다.  
코드 수정 전에 문제를 정확히 정의하고, 요구사항을 추적 가능하게 구조화하며, 이후 단계에서 바로 테스트와 구현으로 이어질 수 있는 산출물을 만드는 역할을 맡는다.

## C. Context
- 프로젝트: 사원 관리 Database 프로그램
- 현재 단계: `SPEC`
- 현재 브랜치 목적: 요구사항 분석, 작업 분해, 규칙 정리, 추적 문서화
- 참조 문서:
  - `@00_작업규칙.TXT`
  - `@01_PJT_전략.TXT`
  - `@02_BRANCH_전략.TXT`
  - `@04_작업시나리오.TXT`
  - `@DOCS/00_PRD.md`
  - `@DOCS/01_epic.md`
  - `@DOCS/02_requirements_traceability.md`
  - `@DOCS/03_gherkin.md`
  - `@DOCS/04_todo.md`
  - `@DOCS/05_README.md`
  - `@requirement/Base.md`
  - `@requirement/Further.md`
- 핵심 기능:
  - 기본: `ADD`, `DEL`, `SCH`
  - 추가: `MOD`, `certi`, 세부 옵션, 비교 옵션, `and/or`
- 브랜치 운영:
  - `main`에서 `SPEC` 생성
  - 개인 브랜치 `A_01_spec ~ A_04_spec` 사용 가능

## T. Task
1. 코드베이스 전체 구조와 주요 클래스/책임을 분석하라.
2. `Base.md`와 `Further.md`를 기준으로 요구사항을 기능 단위로 재정리하라.
3. 명령어/옵션/출력 규칙/제약 조건을 표 또는 목록으로 추적 가능하게 정리하라.
4. 구현 전 반드시 확인해야 할 예외 조건과 경계값을 도출하라.
5. 이후 `RED` 단계에서 실패 테스트를 바로 작성할 수 있도록 테스트 대상 목록을 정리하라.
6. 팀 분업이 가능하도록 4개 작업 단위로 쪼개서 제안하라.
7. 이 단계에서는 production code를 변경하지 말고, 분석/설계/문서 산출물 중심으로 작업하라.
8. 새 문서를 만들거나 수정할 경우 현재 `DOCS`, `report`, `prompting` 규칙과 번호 체계를 따르라.

## F. Format
응답은 Markdown으로 작성하고 아래 순서를 반드시 따른다.

1. 프로젝트 한줄 요약
2. 코드베이스 구조 요약
3. 요구사항 추적표
4. 명령어별 상세 규칙
5. 예외/경계값 목록
6. RED 단계용 테스트 대상 목록
7. 4인 분업안
8. 남은 질문 / 리스크

## 완성형 프롬프트
```text
@00_작업규칙.TXT @01_PJT_전략.TXT @02_BRANCH_전략.TXT @04_작업시나리오.TXT @DOCS/00_PRD.md @DOCS/01_epic.md @DOCS/02_requirements_traceability.md @DOCS/03_gherkin.md @DOCS/04_todo.md @DOCS/05_README.md @requirement/Base.md @requirement/Further.md

당신은 Java 프로젝트의 요구사항 분석가이자 아키텍처 리뷰어다.
현재 작업 단계는 SPEC 브랜치이며, 목적은 구현 전에 문제를 정확히 정의하고 이후 RED 단계에서 바로 실패 테스트를 작성할 수 있도록 분석 산출물을 만드는 것이다.

다음 작업을 수행해줘.
1. 코드베이스 전체 구조와 주요 클래스/책임을 분석해줘.
2. Base/Further 요구사항을 기능 단위로 재정리해줘.
3. ADD, DEL, SCH, MOD와 각 옵션(-p, -f, -l, -m, -y, -d, -g, -ge, -s, -se, -a, -o)의 규칙을 추적 가능하게 정리해줘.
4. 출력 규칙(NONE, 최대 5건, 정렬, 변경 전 출력 등)과 제약사항(입력값, 성능, 형식)을 정리해줘.
5. 이후 RED 단계에서 바로 실패 테스트를 작성할 수 있도록 테스트 대상 목록과 우선순위를 정리해줘.
6. 팀원 4명이 병렬 작업할 수 있도록 A_01_spec ~ A_04_spec 기준 분업안을 제안해줘.
7. 새 문서를 만들거나 수정한다면 현재 DOCS 허브와 산출물 번호 체계에 맞춰 제안해줘.

주의사항:
- 이 단계에서는 production code를 수정하지 말고 분석/문서 산출물 중심으로 작업해줘.
- 요구사항 해석이 애매한 부분은 추정하지 말고 질문 또는 리스크로 분리해줘.
- 응답은 Markdown으로 작성하고, 프로젝트 한줄 요약 -> 코드베이스 구조 요약 -> 요구사항 추적표 -> 명령어별 규칙 -> 예외/경계값 -> RED 단계 테스트 대상 -> 4인 분업안 -> 리스크 순서로 정리해줘.
```
