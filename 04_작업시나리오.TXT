=======================================================================================
## 프로젝트 작업 시나리오
=======================================================================================

1. 문서 목적
- 본 문서는 팀프로젝트의 요구사항 구현, 테스트, 리팩토링, 추가 기능 개발, QA까지의
  전체 작업 흐름을 하나의 시나리오로 정리한 운영 문서이다.
- 참조 문서:
  - 00_작업규칙.TXT
  - 01_PJT_전략.TXT
  - 02_BRANCH_전략.TXT
  - requirement/Base.md
  - requirement/Further.md
  - FeedBackAnalyzer_01/README.md


2. 프로젝트 대상 및 최종 목표
- 대상 프로젝트는 사원 관리 Database 프로그램이다.
- 기본 기능은 ADD, DEL, SCH 이며, 추가 기능으로 MOD, certi 컬럼, 세부 검색 옵션,
  비교 옵션, and/or 조건 검색을 구현한다.
- 최종 목표는 아래 3가지를 동시에 만족하는 것이다.
  1) 요구사항 정합성 확보
  2) 테스트 커버리지 90% 이상 달성
  3) Clean Code / TDD / Refactoring 원칙을 지키는 협업 구조 정착


3. 작업 기본 원칙
- 모든 작업은 통합 브랜치와 개인 작업 브랜치를 분리하여 진행한다.
- 각 단계는 "요구사항 확인 -> 실패 테스트 작성 -> 구현 -> 리팩토링 -> 리뷰" 순서를 따른다.
- 기능 구현과 테스트 구현은 항상 함께 이동한다.
- 커밋은 가능한 한 작게 유지하며, 하나의 의도를 가지도록 작성한다.
- 작업 중 생성되는 분석 문서, 보고서, 프롬프트 기록은 작업규칙의 명명 규칙을 따른다.
- 실행과 검증은 README 스타일처럼 "실행 방법", "검증 방법", "산출물"이 명확히 보이도록 정리한다.


4. 브랜치 운영 시나리오
## 기본 구조
main
 └── SPEC                     ← 통합 브랜치 (main에서 생성)
      ├── A_01_spec           → PR → SPEC 머지
      ├── A_02_spec           → PR → SPEC 머지
      ├── A_03_spec           → PR → SPEC 머지
      ├── A_04_spec           → PR → SPEC 머지
 └── RED                      ← 통합 브랜치 (main에서 생성)
      ├── A_01_RED            → PR → RED 머지
      ├── A_02_RED            → PR → RED 머지
      ├── A_03_RED            → PR → RED 머지
      ├── A_04_RED            → PR → RED 머지
 └── GREEN                    ← 통합 브랜치 (main에서 생성)
      ├── A_01_GREEN          → PR → GREEN 머지
      ├── A_02_GREEN          → PR → GREEN 머지
      ├── A_03_GREEN          → PR → GREEN 머지
      ├── A_04_GREEN          → PR → GREEN 머지
 └── REFACTORING              ← 통합 브랜치 (main에서 생성)
      ├── A_01_REFACTORING    → PR → REFACTORING 머지
      ├── A_02_REFACTORING    → PR → REFACTORING 머지
      ├── A_03_REFACTORING    → PR → REFACTORING 머지
      ├── A_04_REFACTORING    → PR → REFACTORING 머지
 └── NEW_FEATURE              ← 통합 브랜치 (main에서 생성)
      ├── A_01_NEW_FEATURE    → PR → NEW_FEATURE 머지
      ├── A_02_NEW_FEATURE    → PR → NEW_FEATURE 머지
      ├── A_03_NEW_FEATURE    → PR → NEW_FEATURE 머지
      ├── A_04_NEW_FEATURE    → PR → NEW_FEATURE 머지
 └── QA                       ← 통합 브랜치 (main에서 생성)
      ├── A_01_QA             → PR → QA 머지
      ├── A_02_QA             → PR → QA 머지
      ├── A_03_QA             → PR → QA 머지
      ├── A_04_QA             → PR → QA 머지

- `main`
  - 최종 제출 또는 배포 기준 브랜치
- `SPEC`
  - 요구사항 분석, 규칙 정의, 추적 문서화, 작업 분해를 위한 통합 브랜치
- `RED`
  - 실패 테스트 작성과 테스트 구조 개선을 위한 통합 브랜치
- `GREEN`
  - 기본 요구사항 기준 기능 동작을 맞추는 구현 통합 브랜치
- `REFACTORING`
  - 동작 보존 상태에서 구조를 개선하는 통합 브랜치
- `NEW_FEATURE`
  - Further.md 기반 추가 기능 구현 통합 브랜치
- `QA`
  - 최종 검증, 비교 보고서, 커버리지 점검, 제출용 결과 정리 통합 브랜치

- 팀원 작업 방식
  - 각 단계는 `main`에서 통합 브랜치를 생성하여 시작한다.
  - 각 통합 브랜치에서는 4개의 개인 작업 브랜치로 분할하여 병렬 작업을 수행한다.
  - 예시:
    - `A_01_spec` -> PR -> `SPEC`
    - `A_02_RED` -> PR -> `RED`
    - `A_03_GREEN` -> PR -> `GREEN`
    - `A_04_REFACTORING` -> PR -> `REFACTORING`
    - `A_01_NEW_FEATURE` -> PR -> `NEW_FEATURE`
    - `A_02_QA` -> PR -> `QA`
  - 개인 브랜치에서는 하나의 작업 주제만 수행한다.
  - 개인 브랜치 머지 후 통합 브랜치 기준으로 리뷰, 재검증, 다음 단계 진입 여부를 결정한다.


5. 단계별 작업 시나리오
1단계. SPEC 단계 - 문제 이해와 작업 분해
(통합 브랜치: SPEC / 개인 브랜치: A_01_spec ~ A_04_spec)
---------------------------------------------------------------------------------------
[입력]
- Base.md
- Further.md
- 기존 소스 구조
- README 형식 참고 자료

[주요 작업]
- 프로젝트 전체 구조와 핵심 도메인 분석
- 명령어 단위 요구사항 정리
  - ADD
  - DEL
  - SCH
  - MOD
- 컬럼 및 옵션 정리
  - employeeNum, name, cl, phoneNum, birthday, certi
  - -p, -f, -l, -m, -y, -d, -g, -ge, -s, -se, -a, -o
- 요구사항 추적표 작성
- 구현 우선순위와 작업 단위 분해
- 예외/경계값 목록 정리
- 10만 건 처리, 출력 5건 제한, NONE 출력, 정렬 규칙 같은 품질 조건 확인

[권장 분담]
- A_01_spec: Base.md 핵심 기능 분석
- A_02_spec: Further.md 추가 기능 분석
- A_03_spec: 옵션/출력 규칙/예외 케이스 정리
- A_04_spec: 요구사항 추적표 및 TODO 정리

[산출물]
- 요구사항 요약 문서
- 기능 목록 / 우선순위 문서
- 테스트 대상 목록
- 작업 TODO

[종료 조건]
- 팀원 모두가 동일한 요구사항 해석을 공유한다.
- 이후 RED 단계에서 바로 실패 테스트를 쓸 수 있을 정도로 규칙이 정리된다.


2단계. RED 단계 - 실패 테스트 우선 작성
(통합 브랜치: RED / 개인 브랜치: A_01_RED ~ A_04_RED)
---------------------------------------------------------------------------------------
[입력]
- SPEC 단계 산출물
- 현재 구현 코드

[주요 작업]
- JUnit 5 기반 테스트 구조 정비
- 클래스별 단위 테스트 작성
- 명령어별 실패 테스트 작성
- 입력 검증 테스트 작성
- 출력 옵션 테스트 작성
- 정렬/최대 5건/NONE 테스트 작성
- 추가 요구사항 대상 테스트 초안 작성

[우선 테스트 항목]
- ADD 입력 형식 및 필드 유효성
- DEL / SCH 기본 조건 검색
- -p 옵션 유무에 따른 출력 차이
- 정렬 기준(입사년도 우선)
- MOD 변경 전 출력 규칙
- certi 컬럼 포함 출력
- 이름/전화번호/생년월일 세부 옵션
- 비교 검색 옵션
- and/or 조합 조건

[권장 분담]
- A_01_RED: 필드/도메인 단위 테스트
- A_02_RED: ADD / DEL / SCH 기본 테스트
- A_03_RED: 출력 옵션 / NONE / 정렬 테스트
- A_04_RED: MOD / certi / 추가 옵션 실패 테스트 초안

[산출물]
- 실패 테스트 케이스
- 테스트 데이터 파일
- 커버리지 기준 문서

[종료 조건]
- 구현되지 않았거나 잘못된 기능이 테스트에서 명확히 드러난다.
- GREEN 단계에서 무엇을 고쳐야 하는지 목록이 분명하다.


3단계. GREEN 단계 - 기본 요구사항 동작 완성
(통합 브랜치: GREEN / 개인 브랜치: A_01_GREEN ~ A_04_GREEN)
---------------------------------------------------------------------------------------
[입력]
- RED 단계 실패 테스트
- Base.md 기본 요구사항

[주요 작업]
- ADD, DEL, SCH 기본 동작 구현 또는 수정
- 출력 형식 맞춤
- 출력 옵션(-p) 처리
- 결과 건수 출력 처리
- NONE 처리
- 정렬 및 최대 5건 제한 구현
- main 실행 경로 점검
  - `EmployeeManagement [input 파일] [output 파일]`

[권장 분담]
- A_01_GREEN: ADD 및 입력 검증
- A_02_GREEN: DEL 기능과 결과 출력
- A_03_GREEN: SCH 기능과 검색 결과 출력
- A_04_GREEN: 정렬 / 최대 5건 / NONE / 실행 경로 보완

[산출물]
- 기본 요구사항 통과 코드
- 테스트 통과 결과

[종료 조건]
- Base.md 요구사항 관련 테스트가 모두 통과한다.
- 프로그램이 입력 파일을 읽고 결과 파일을 생성한다.


4단계. REFACTORING 단계 - 구조 개선
(통합 브랜치: REFACTORING / 개인 브랜치: A_01_REFACTORING ~ A_04_REFACTORING)
---------------------------------------------------------------------------------------
[입력]
- GREEN 단계에서 동작이 보장된 코드

[주요 작업]
- 의미 없는 변수명/메서드명 개선
- 매직 넘버 상수화
- 20줄 이상 메서드 분리
- 중복 로직 공통화
- 클래스 책임 재배치
- SRP/OCP 관점의 구조 개선
- 외부 계약과 출력 형식은 유지

[권장 분담]
- A_01_REFACTORING: 네이밍 개선
- A_02_REFACTORING: 매직 넘버 / 상수 정리
- A_03_REFACTORING: 긴 메서드 분리 및 중복 제거
- A_04_REFACTORING: 책임 분리 / 구조 재배치

[산출물]
- 리팩토링 결과 코드
- 전/후 비교 메모

[종료 조건]
- 테스트는 계속 GREEN 상태를 유지한다.
- 가독성과 유지보수성이 개선되며 기능 동작은 변하지 않는다.


5단계. NEW_FEATURE 단계 - 추가 요구사항 구현
(통합 브랜치: NEW_FEATURE / 개인 브랜치: A_01_NEW_FEATURE ~ A_04_NEW_FEATURE)
---------------------------------------------------------------------------------------
[입력]
- Further.md
- RED 단계 테스트 초안

[주요 작업]
- MOD 명령 구현
- certi 컬럼 추가
- 이름 옵션(-f, -l) 구현
- 전화번호 옵션(-m, -l) 구현
- 생년월일 옵션(-y, -m, -d) 구현
- SCH 전용 비교 옵션(-g, -ge, -s, -se) 구현
- and/or 조건 검색(-a, -o) 구현
- 각 기능별 테스트 보강

[권장 구현 순서]
1) certi 컬럼 반영
2) MOD 구현
3) 이름/전화번호/생년월일 세부 옵션
4) 비교 검색 옵션
5) and/or 조합 옵션

[권장 분담]
- A_01_NEW_FEATURE: certi 컬럼 및 출력 반영
- A_02_NEW_FEATURE: MOD 명령 구현
- A_03_NEW_FEATURE: 이름 / 전화번호 / 생년월일 세부 옵션
- A_04_NEW_FEATURE: 비교 검색 / and-or 조합 옵션

[산출물]
- 추가 기능 구현 코드
- 추가 기능 테스트

[종료 조건]
- Further.md의 기능 요구사항이 모두 테스트로 검증된다.
- 기존 기능 회귀가 발생하지 않는다.


6단계. QA 단계 - 최종 검증 및 제출 정리
(통합 브랜치: QA / 개인 브랜치: A_01_QA ~ A_04_QA)
---------------------------------------------------------------------------------------
[입력]
- REFACTORING / NEW_FEATURE 결과
- 테스트 결과

[주요 작업]
- 커버리지 점검
- 통합 테스트 수행
- 성능 관점 기본 확인(대량 데이터 처리 가능성 검토)
- 리팩토링 전후 비교 보고서 작성
- 남은 리스크 및 미해결 이슈 정리
- 제출용 README / 보고서 / 작업기록 정리

[권장 분담]
- A_01_QA: 커버리지 및 테스트 결과 점검
- A_02_QA: 통합 시나리오 및 회귀 테스트
- A_03_QA: 비교 보고서 / 리스크 문서화
- A_04_QA: 제출용 README / 보고서 / 기록 정리

[산출물]
- 최종 작업 보고서
- QA 점검 결과
- 제출용 문서 묶음

[종료 조건]
- 요구사항, 품질, 협업 기록이 함께 정리된다.
- QA 통합 브랜치 검토 후 main 병합 준비가 완료된다.


6. 1회 작업 단위의 실제 실행 흐름
---------------------------------------------------------------------------------------
1) `main` 최신화
2) 해당 단계의 통합 브랜치 생성 또는 최신화
3) 개인 작업 브랜치 1개 생성
4) 작업 범위 1건 선정
5) 요구사항과 기존 테스트 확인
6) 실패 테스트 먼저 작성
7) 최소 구현으로 테스트 통과
8) 리팩토링
9) 로컬 테스트 재실행
10) 문서/보고서/프롬프트 기록 정리
11) PR 생성 후 리뷰 반영
12) 개인 브랜치를 통합 브랜치에 머지
13) 통합 브랜치 기준 재검증 후 다음 단계 진행


7. 산출물 관리 규칙
---------------------------------------------------------------------------------------
- docs/
  - 분석 문서, 요구사항 정리, 설계 문서 저장
  - 형식: `{순번2자리}_{제목}.md`
- report/
  - 작업 결과 보고서 저장
  - 형식: `{순번2자리}_{제목}.md`
- prompting/
  - agent와의 작업 대화 기록 저장
  - 형식: `{순번2자리}_{제목}.md`
- 추가 기록
  - `User_prompt.md`: 사용자 프롬프트만 별도 정리
  - `GIT_prompt.md`: 사용한 git 명령어만 중복 없이 정리


8. 역할 분담 예시
---------------------------------------------------------------------------------------
- 팀원 A: 요구사항 분석 / 명령 파서 / 문서화
- 팀원 B: ADD / DEL / SCH 기본 기능 및 출력 규칙
- 팀원 C: 테스트 구조 / 승인 테스트 / 커버리지 관리
- 팀원 D: MOD / certi / 세부 옵션 / and/or 구현
- 공통: 리뷰, 리팩토링, QA

10. 결론
- 본 프로젝트는 단순 기능 구현보다도 "요구사항 추적 + 테스트 우선 + 작은 단위 협업"이 중요하다.
- 따라서 작업은 반드시 SPEC -> RED -> GREEN -> REFACTORING -> NEW_FEATURE -> QA 순서로 관리한다.
- 각 단계는 `main`에서 생성한 통합 브랜치와 4개의 개인 브랜치를 함께 운영하는 방식으로 진행한다.
- 각 단계는 코드만 남기는 것이 아니라, 분석 문서와 결과 보고서까지 남겨 팀의 학습과 제출 품질을 함께 높인다.
